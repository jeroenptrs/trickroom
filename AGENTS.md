# Trickroom

Trickroom helps designers and agents work on UI using code-native primitives, with local-first design data that stays close to the implementation.

## What we're shipping

Trickroom is a design tool purpose-built to live as close to the code as possible. The ethos is "Design is Code", and to use what we have available to its fullest. We live at the convergence of design and development, making the handoff from design to code as straightforward as possible.

The ergonomics should be designer focused but with the addition of agents (via MCP) being able to collaborate, propose ideas, and provide code-to-design imports or design-to-code exports ensuring everything stays in sync.

We split this up into Designs and Systems, where designs contain the actual interactive designs users and agents collaborate on, and Systems that contain the entire design system that a Design can consume.

## What we're not shipping

There is no intention for this to grow into a no-code webdev platform. No custom rendering mechanisms that recreate foundational CSS and layout intricacies in a canvas element. No obfuscating data, all properties are available for users and agents to render this down to HTML and CSS themselves.

## Product principles

- Everything generated by Trickroom should be reviewable with git diffs, code review, and agent-readable structured edits
- Storage should not be a proprietary format, for example design files are JSON structured to represent JSX-like trees as reliably as possible
- Components are user-owned and can be styled, Recipes are library-owned and generally unstyled/headless (with the occasional sensible default as the exception)
- Performance is the right mindset, design and component files can get huge, as can icon and asset libraries, to render this performantly and reliably without any stutter or jank is core to the mission
- Do not reinvent what already exists. Before introducing Trickroom-specific primitives, check whether React, React-adjacent libraries, TypeScript, Tailwind, or Tailwind internals already solve the problem. For example: leveraging Tailwind internals more and more for both managing tokens as well as inside design and system editors
- Changing data comes with migrating that data to its new shape. Persisted shapes in userland need a migration path (best example: Components)

## Positioning

Trickroom borrows familiar visual-editing affordances, but the source of truth should remain native to the code. Designer familiarity is a UI goal while transparent, local-first, React/HTML/CSS/Tailwind-compatible data is a product constraint.

When those conflict, preserve the code-native model and find the closest designer-friendly expression on top of it.

## Glossary

- you: the agent 
- I/me: the lead developer you're interfacing with
- we/us/our: agents and developers working on Trickroom
- designers/developers/they/users: our core audience, possibly designing for a codebase, or using the design to further the ui for the application they're building

- Trickroom: the app we're building
- Project: the codebase users are using Trickroom in, their data is stored inside a (preferably) committed `.trickroom` folder
- Design (file): a file containing a design or multiple designs 
  - Layer: any layer inside the Design file or in a Component
  - Board: a root layer inside a Design file, can be used to separate/paginate related designs
- System (file): the collection of tokens, icons, assets, fonts and components that together gives a user all building blocks for a Design System
  - Token: a representation of an atomic styling element (e.g. color, font, text size, ...) that collectively builds towards an encompassing design system
  - Icon: an svg asset, added as a folder of svgs (icon library)
  - Asset: media asset (image/video, that currently is not an svg) that can be embedded in a Design file
  - Component: a user authored collection of layers and variants built for use and reuse inside Design files
- Library: a headless component library whose Elements you can use inside of a Design file or Component
  - Element: a React component, usually headless, potentially part of a composable UI concept like menus, dialogs, etc.
  - Registry: the registry containing a Library's Elements
  - Recipe: a building block composed of multiple Elements that presents a full UI concept (the aforementioned menus, dialogs, etc.)
- Variant: a variation of (a part of) a Component like primary or secondary, large medium or small, etc.
  - Compound Variant: styling added to a specific combination of Variant values
- Slot: part of a Component or Recipe that invites users to put layers of their own choosing inside
- Instance: the placed copy of a Component or Recipe in a Design
- Detach: severing an Instance from the Component/Recipe it is referencing

## Working in this repo

TypeScript + React 19 + Vite + Electron + Tailwind v4 + MCP server, managed with pnpm.

- `pnpm dev` — browser app (regenerates Tailwind tokens first); `pnpm electron:dev:hot` for the desktop shell
- `pnpm test` — vitest, single run
- `biome check --write` — lint + format (tabs, double quotes)
- Typecheck with `tsc -b`. The bare `tsc` in build scripts checks nothing. There is a pre-existing error baseline; only errors in files you touched are yours.

Conventions and gotchas:

- tv()/cva() styling lives only in `src/components/ui/` primitives; import the variant function elsewhere (biome enforces this)
- Prefer flexbox; reserve CSS grid for genuinely two-dimensional layouts
- Visual language is brutalist: slate + cyan, square corners, IBM Plex. Don't soften it
- Concurrent agent sessions may share this working tree: stage and commit by path, never `git stash` or `git add -A`
- Persisted userland shapes need migrations — see `src/services/` for the revision and migration patterns (e.g. system components)

Full docs in `docs/` — start at `docs/README.md`; `docs/architecture.md` for runtime layout, `docs/mcp.md` for agent tooling, `docs/development.md` for the complete script/packaging reference.
