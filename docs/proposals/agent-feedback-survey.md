# Agent feedback survey

Status: research, 2026-10-14. Input for the "actionable feedback for agents" feature (annotations on layers, picked up by agents over MCP) and a possible structured steering feature after it.

Method: vendor docs, changelogs, launch posts, GitHub source and npm packages, fetched on 2026-10-14. Most help-center pages carry no date and are marked "undated". Forum posts and third-party write-ups are marked "secondary". Claims I could not confirm from any source are marked UNVERIFIED. The surveyed products change monthly, so expect parts of this to be out of date by the time we build.

## What we compare against

Trickroom today has single-layer selection in the Layers rail (no click-to-select on the canvas yet). `editor_context` tells an agent what the human has open and selected, and `editor_focus` moves the human's view. The editor flashes layers an agent changed and keeps "changed externally" markers on them until the human has seen them. Per-design memory notes hold intent, conventions and decisions. Board-level content-hash revisions let concurrent human and agent writes merge. The opt-in audit log (`.trickroom/audit-log.jsonl`) records every MCP write. The conversation stays in the harness (Claude Code, Codex, T3 Code), and we are not building a chat panel.

## Per-tool notes

Numbers refer to the seven questions: (1) select-and-comment, (2) change review, (3) mid-generation steering, (4) thread lifecycle, (5) handoff outside the tool, (6) direct manipulation vs prompting, (7) intent and memory. Questions a tool's docs don't answer are left out.

### Claude Design and Claude Code artifacts

- (1) Click a canvas element to comment ([get started](https://support.claude.com/en/articles/14604416-get-started-with-claude-design), undated). Comment mode shows an open-comment count, per-comment replies and a "Send to Claude" checkbox that separates requests for Claude from notes for teammates ([article 17457950](https://support.claude.com/en/articles/17457950), undated). Target format UNVERIFIED. (2) "Claude Design doesn't have version history yet." (3) You can "queue multiple messages or keep chatting while Claude works" ([Claude blog](https://claude.com/blog/how-the-product-designer-who-built-claude-design-uses-it-to-explore-ideas-before-building-them), 2026-07-24). (4) The help center admits comments "disappear before Claude reads them" and suggests pasting feedback into chat. (5) Export hands off to a local coding agent or Claude Code Web. Whether comments travel is UNVERIFIED. (6) Edit mode drags and resizes directly, and "direct edits use no tokens". Claude can generate sliders bound to design parameters ([launch post](https://www.anthropic.com/news/claude-design-anthropic-labs), 2026-04-17). (7) Design systems built from code and design files. The standalone claude.ai/design closes 2026-12-14 in favour of `/design` inside conversations and Claude Code.
- Claude Code artifact comments ([docs](https://code.claude.com/docs/en/artifacts), undated, v2.1.221+) are the closest Anthropic precedent. An editor activates a thread with "Send to Claude" or `@claude`, and Claude can reply to or resolve only activated threads. Claude Code watches a published artifact, and a sent comment "reaches your session right away". Permission mode decides whether Claude replies unasked. Auto-replies cap at 60 per artifact per hour, and Ctrl+C at an idle prompt pauses them.

### Harness element pickers and steering

- **Claude Code desktop.** "Select an element" in the Browser pane (Cmd+Shift+S) ([desktop docs](https://code.claude.com/docs/en/desktop), undated). The payload is undocumented. Diff line comments are batched and submitted together. A message queued during a turn reaches Claude "as soon as those tool calls finish, within the same turn" ([interactive mode](https://code.claude.com/docs/en/interactive-mode), undated). Queued messages show grey until Claude starts on them.
- **Cursor Design Mode** ([docs](https://cursor.com/docs/agent/design-mode); [3.7 changelog](https://www.cursor.com/changelog/design-mode-improvements), 2026-06-05). Click, multi-select, Shift+drag an area, draw on a frozen frame, or speak. The agent gets "the xpath, the component, attributes, computed styles, and props from the fiber tree" plus a screenshot. Each edit runs as its own agent. "Send now" delivers "at the agent's next tool call instead of cutting off work mid-action" ([tabs docs](https://cursor.com/docs/agent/chat/tabs), undated).
- **Codex app.** Annotate mode in the in-app browser: click or drag, comment, repeat, then ask Codex in chat to address the comments. An "Adjust" control previews font, spacing and colour changes ([browser docs](https://learn.chatgpt.com/docs/browser.md?surface=app), undated). Steer "adds the message to the current run", Queue saves it for the next ([prompting](https://learn.chatgpt.com/docs/prompting), undated).
- **VS Code / Copilot.** "Comment on Elements" (1.132) attaches a comment per element, several per send ([integrated browser](https://code.visualstudio.com/docs/debugtest/integrated-browser), 2026-10-07). Steer, the default, "yields after finishing the current tool execution" ([chat agent](https://code.visualstudio.com/docs/copilot/chat/chat-agent-mode), undated). On diffs, "the agent reads your comments, makes the requested edits, and resolves each comment", and "Mark as Reviewed" clears "if you or the agent changes the file again" ([review](https://code.visualstudio.com/docs/copilot/chat/review-code-edits), 2026-10-07).
- **Zed.** Steer on a queued message lands "between a tool call and a response". "Steering is only available for the Zed Agent, since Zed can't detect turn boundaries for external agents" ([agent panel](https://zed.dev/docs/ai/agent-panel), undated).
- **Windsurf / Devin Desktop.** "Send element" adds elements to the prompt as @-mentions ([previews](https://docs.devin.ai/desktop/previews), undated).

Apart from VS Code's diff comments, none keep a thread or state on the element. The comment becomes prompt text and is gone.

### Figma

- **Make.** (1) "Annotate for agent" drops numbered annotations on the preview, stacked and submitted "together as a single prompt" ([help](https://help.figma.com/hc/en-us/articles/42009840449175), undated; [blog](https://figma.com/blog/properties-panel-and-annotations-now-in-figma-make), 2026-07-30). Property edits stage above the prompt box until Apply. (2) Every edit creates a version. No diff, no per-change undo. (3) Prompts typed during a run join an editable queue ([help](https://help.figma.com/hc/en-us/articles/31304485164695), undated). (4) Annotations have no state. (7) `Guidelines.md`, which Make reads first.
- **Figma agent** ([blog](https://www.figma.com/blog/the-figma-agent-is-here/), 2026-05-20). Prompt on a selected layer. Undo reverts only the last change, and "there's no selective revert" ([forum, staff](https://forum.figma.com/ask-the-community-7/does-figma-ai-agent-support-undo-55401), 2026-06-30). It can "take action on comments". Resolving them is UNVERIFIED.
- **Comments** ([REST types](https://developers.figma.com/docs/rest-api/comments-types/), undated). Anchors are canvas `{x,y}`, `{node_id, node_offset}`, or a region with a pin corner. Two-level threads via `parent_id`. Resolution is a nullable `resolved_at` that no endpoint can set. Cut-and-paste "disconnects" a comment, with no reattach ([help](https://help.figma.com/hc/en-us/articles/360041547853), undated). Dev Mode annotations are a separate object on the node, `{label, properties[], categoryId}`, with no state ([Plugin API](https://developers.figma.com/docs/plugins/api/Annotation/)).
- **MCP server** ([tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/), undated). Reads plus `use_figma` writes since March 2026 ([blog](https://www.figma.com/blog/the-figma-canvas-is-now-open-to-agents/), 2026-03-24). No comments tool, and a request open since 2026-04-01 has no staff reply ([forum](https://forum.figma.com/suggest-a-feature-11/feature-request-figma-mcp-support-for-comments-52526/index2.html)). Dev Mode annotations surface only as a `data-annotations` attribute in a per-node read, which users had to discover ([forum](https://forum.figma.com/suggest-a-feature-11/mcp-support-for-annotations-53685), 2026-06).

### Onlook, v0, Lovable, Bolt

- **Onlook.** Injects `data-oid` into JSX and maps it to file, line range and component ([ids.ts](https://github.com/onlook-dev/onlook/blob/main/packages/parser/src/ids.ts)). Selection builds chat context automatically. A git checkpoint per chat message. Messages typed while streaming queue until it ends. Visual edits write code deterministically. Comments are an unchecked roadmap item ([README](https://github.com/onlook-dev/onlook)). The Mac app hands off as a PR ([docs](https://docs.onlook.com/handoff/what-your-engineers-see), undated).
- **v0.** Design Mode attaches a screenshot of the element. The API sends `selectorPath` and `reactComponentName` as "hints", "not checked preconditions" ([API guide](https://v0.app/docs/api/v2/guides/design-mode), undated). Annotations mode batches numbered comments (changelog, 2026-06-19). Diff tab per version. Up to 10 queued prompts, Cmd+Enter interrupts ([changelog](https://v0.app/changelog), 2026-07-31). Panel edits go through the model.
- **Vercel Toolbar** comments are the one hosted comment system built for agents. Threads are resolved or unresolved, and anyone can reopen. Vercel MCP lists, reads, replies to and resolves threads (`list_toolbar_threads`, `reply_to_toolbar_thread`, `change_toolbar_thread_resolve_status`, ...) ([tools](https://vercel.com/docs/agent-resources/vercel-mcp/tools/toolbar)). `vercel comments resolve <id> -m "..."` replies and resolves in one call ([changelog](https://vercel.com/changelog/manage-vercel-toolbar-comments-from-the-cli), 2026-08-20). Pull only.
- **Lovable.** Select (multi), Draw and Comment modes ([toolbar](https://docs.lovable.dev/features/preview-toolbar.md), undated). `lovable-tagger` records `file:line:column` per node. Comment pins anchor by page structure, and a detached thread is kept and flagged ([comments](https://docs.lovable.dev/features/project-comments.md)). Follow-ups are read "at its next natural stopping point" ([build mode](https://docs.lovable.dev/features/agent-mode.md)), while comment threads "run after the current task". The agent answers in chat, not in the thread. Versions with diff and all-or-nothing revert. MCP exposes no comments. Knowledge is 10,000 characters, always in context.
- **Bolt.** One-element Select tool, and area-pinned comments ([comments](https://support.bolt.new/building/using-bolt/comments), undated). Comments are open, resolved or detached, and reattach when a version restore brings the element back. Sending comments to Bolt marks them resolved, and the reply lands in chat. A strict queue: "no way to send a prompt that bypasses the queue". Visual edits cost tokens on save.

### Annotation-for-agent tools

- **Agentation** ([MCP](https://www.agentation.com/mcp), [schema](https://www.agentation.com/schema), 3.1.2 on 2026-09-22) has the most complete lifecycle. `status: pending | acknowledged | resolved | dismissed`, `resolvedBy: human | agent`, `intent: fix | change | question | approve`, `severity`, and `thread: [{id, role, content, timestamp}]`. The target is a CSS path plus React components and `path:line:column`. - **Vibe Annotations** ([architecture](https://www.vibe-annotations.com/docs/architecture)). MCP `read_annotations`, `watch_annotations`, `delete_annotation`. Annotations can carry CSS diffs from live tweaks. No states: the agent deletes what it finished. Stored under `~/`.
- **Drawbridge** ([GitHub](https://github.com/breschio/drawbridge)). Writes `.moat/moat-tasks.md`, `.moat/moat-tasks-detail.json` and screenshots into the repo, plus slash commands for Claude Code, Codex and Windsurf. Tasks are `to do | doing | done`.
- **Stagewise** sent selected elements to Cursor and Windsurf through editor extensions in 2025. It deprecated that toolbar and is now its own IDE ([npm](https://registry.npmjs.org/@stagewise/toolbar); [docs](https://docs.stagewise.io/core-concepts/browser-and-agent), 2026-08-04).

### Comment-to-agent loops elsewhere

- **GitHub.** Copilot coding agent acts on `@copilot` PR comments ([docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs)). Thread resolution needs a GraphQL thread id that REST tools do not return, so agents cannot close threads they read.
- **Linear agents** ([docs](https://linear.app/developers/agent-interaction)). Sessions are `pending | active | error | awaitingInput | complete | stale`, and a `prompted` webhook delivers a human follow-up into a running session.
- **Claude Code Channels** ([reference](https://code.claude.com/docs/en/channels-reference), research preview). An MCP server can push `notifications/claude/channel` events, but "if several notifications arrive while Claude is busy, they're delivered together on the next turn". Custom channels need `--dangerously-load-development-channels` and do not run with `-p` or the Agent SDK.
- **MCP spec 2026-07-28** drops protocol sessions and moves notifications to an opt-in `subscriptions/listen` stream ([blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)).

## Patterns that recur and seem to work

**Batch, then send.** Figma Make, v0, Codex, VS Code 1.132, Bolt, Subframe's live-edit tray and Claude Code's diff comments all let the human stack several element-anchored notes and send them in one go. Nobody sends each note as it is typed. The reasons hold for Trickroom too. A half-written note should not reach the agent, related notes ("match A to B") belong together, and one batch means one round of agent work. Claude Code artifacts add a per-thread flag ("Send to Claude") that separates requests for the agent from notes between people.

**Delivery at tool-call boundaries.** Claude Code passes queued messages to Claude "as soon as those tool calls finish, within the same turn". Cursor delivers "Send now" at "the agent's next tool call". VS Code's steer yields after the current tool, Zed's at "its next step", Polymet's at "its next step". Lovable reads follow-ups "at its next natural stopping point". They agree on the boundary that works: between tool calls, never mid-action, keeping completed work. Tools that only queue for the next turn (Bolt, Onlook, Subframe, Figma Make as documented) give up exactly what we want. Zed's docs also say why a host cannot do this for someone else's agent: "Zed can't detect turn boundaries for external agents." Trickroom is in the same position as an MCP server. Our only turn boundary is the moment our own tool returns.

**Pull tools, not push.** Every external-agent integration that works is pull-based. Vercel lists unresolved threads, Subframe has `list_comments`, Agentation and Vibe use blocking `watch` calls. The one push mechanism, Claude Code Channels, is a research preview, needs a development flag for custom servers, and delivers events that arrive during a busy turn "on the next turn". The 2026-07-28 MCP spec moved notifications to an opt-in stream. A design that needs push will work in one harness at best.

**Explicit states with a split between "the agent did it" and "the human accepts it".** Agentation records `resolvedBy`. Claude Code artifacts let Claude resolve only threads a person activated. Vercel lets anyone resolve but makes the closing reply part of the resolve call. Magic Patterns' "Needs you" state and VS Code's "Mark as Reviewed", which clears when the agent touches the file again, both mark work that waits for the human. Bolt shows what goes wrong without the split: sending a comment marks it resolved, so "resolved" means "sent", and the human cannot tell what was actually fixed.

**Detached, not deleted.** Bolt and Lovable keep a thread when its element disappears, label it detached, and Bolt reattaches it when a version restore brings the element back. Figma's cut-and-paste orphans comments with no repair, and users have been asking for reattachment for years.

**Thread ids in every result.** The GitHub MCP thread-id gap and Figma's webhook without an anchor show the same failure. If a listing does not return the id and anchor the next call needs, agents cannot close the loop.

**Always-read intent files.** Lovable Knowledge, Subframe's always-read guidelines document, Figma Make's `Guidelines.md` and Stitch's DESIGN.md all put a short intent document in front of the agent every time. Trickroom's memory notes are explicitly never added on their own. That is defensible for size, but the evidence says agents use what they are handed and skip what they have to fetch. Figma's annotations-in-`data-annotations` episode, where users had to tell agents where to look, is a small example.

## Patterns that belong to in-tool chat products

- **Annotation as prompt text.** In v0, Make, Lovable, Bolt, Codex and Cursor the annotation is compiled into a chat message and then exists only in the transcript. That works when the tool owns the transcript. Trickroom does not own one, and the harness transcript is not shared with the designer, so a Trickroom annotation must live as data on disk or it is lost.
- **Replies that land in chat.** Lovable and Bolt post the agent's answer in the chat, not under the comment. Without our own chat, the reply under the annotation is the only place a designer will see what the agent did.
- **Credit-metered staged edits.** v0, Bolt and Figma Make route panel edits through the model and charge for it. Trickroom's inspector already writes the JSON deterministically, as Onlook's visual edits do. We have nothing to stage or charge for.
- **Interrupt and queue controls.** Queue vs steer, Cmd+Enter to interrupt, reorderable queues: these sit in the harness for Trickroom users. Claude Code, Codex, Cursor and T3 Code each ship their own. We should not rebuild them. We control what our tool results contain, which decides what the agent sees at the boundary.
- **Variation trays and generated sliders.** Subframe's three variations with Keep or Discard and Claude Design's generated sliders assume the tool runs the model and can ask for N outputs. An external agent could write variants as sibling boards, but no UI is needed for that in the first version.
- **Screenshot-only targets.** Stitch's drawn annotations and v0's element screenshots exist because those tools have no stable element identity they trust. We have layer ids.

## Recommendations for Trickroom

### Adopt

1. **Layer-id anchors with a fallback snapshot.** Anchor an annotation to `{ boardId, elementId }`, or to a board, the design, or a component node (`componentId`, node id, variant values) in the component editor. Store a snapshot alongside it: layer name, component, the chain of ancestor names, and the design revision at creation. Add the stage mode and responsive width the human was looking at. Vercel and Vibe both record viewport, and a Trickroom board is reviewed at several widths, so "this wraps badly" means nothing without the width. Make an optional offset or region inside the layer (Figma's `FrameOffsetRegion`) available for "this gap here" comments, but keep the layer as the anchor.
2. **Detached as a derived flag, not a state.** When the anchored element no longer exists, show the thread as detached with its snapshot, and reattach when the id comes back (git checkout, undo, `Take theirs`). Watch for operations that change ids. `copySubtree` and component detach mint new ids. A delete-and-recreate by an agent orphans the thread even when the layer looks the same. Have `design_apply` warn when a step deletes an element with open annotations, and accept an explicit re-anchor.
3. **A lifecycle with the split between addressed and resolved.** Proposed states: `open`, `acknowledged` (an agent saw it, set automatically when the annotation first appears in a tool result for that session), `addressed` (the agent replied with a change record), `needs_input` (the agent asked a question, after Linear's `awaitingInput`), `resolved` and `dismissed`. Only the human sets `resolved`. The agent can propose `dismissed` with a reason, and the human confirms. A human reply on an addressed or resolved thread reopens it. Record `by` on every transition, as Agentation does with `resolvedBy`. Keep state per annotation, not per batch. When a batch of five comes back with four addressed, the fifth stays open on its own, which gives the human Polymet's "retry only the changes that didn't land" without a separate check.
4. **Reply and write in one call.** Vercel's `resolve -m` is the right instinct, and we can go further. Add an optional `addresses: [{ annotationId, reply }]` to `design_apply`. The service writes the design change, the change record and the thread transition under the same per-design lock in one journaled multi-file write. The reply cannot then describe a change that was refused with `REVISION_MISMATCH`. A separate tool covers replies without a write: acknowledge, question, propose dismissal.
5. **Batch, then send, in the editor.** Draft annotations stay in browser state until the human presses Send (or a per-annotation "for agent" toggle, after Claude Code's "Send to Claude"). This matters more for us than for chat tools. Once open annotations ride on every tool result, anything saved to disk is in front of a working agent within seconds.

### Adapt

6. **Surfacing in tool results, with a cursor.** This is the right mechanism. Delivery between tool calls is what the harnesses converge on, and it needs no push. Three changes to the proposed shape:
   - Keep a per-MCP-session cursor (Agentation's monotonic `sequence`) and include full bodies only for annotations that are new or changed since that session last saw them. On later calls send only a count and ids. Repeating every open annotation on every `design_read` would cost tokens on large designs, and agents learn to skip repeated blocks.
   - Scope by design. Results from `design_read`, `design_apply`, `design_validate`, `design_screenshot` and `editor_context` carry the open annotations of the design they touched. `project_list` and `design_list` carry counts per design.
   - Phrase the block as an instruction with the next call spelled out ("2 new annotations on board Checkout. Address them, or reply with a question: ..."). Figma's annotations sat in a node attribute, and users had to tell agents to look there.
7. **A blocking wait tool for idle agents.** Surfacing in results only reaches an agent that is calling Trickroom tools. For "keep working on my feedback" sessions, add a `watch`-style tool that blocks until sent annotations arrive, with a batch window and a timeout, like Agentation's `watch_annotations`. Treat a Claude Code channel as an optional later addition for Claude Code users. It adds no same-turn delivery (busy-turn events wait for the next turn) and needs a development flag today.
8. **Change records that can be reviewed and reverted.** The record attached to the reply holds the revision before and after, the boards and layer ids touched, the operation list and a one-line summary. That covers review: clicking it calls the same reveal-and-flash path the editor uses for external changes. Revert is the gap every tool leaves open. Figma's agent undoes only its last change, Lovable and Bolt revert whole versions, and Subframe says stopping the agent "does not undo files it already changed". Keep the before-state of the touched layers in the record, so "revert this change" works while those layers have not changed since, and refuses when they have, using the board-revision check we already have. The audit log is opt-in and lives outside the design folder, so it cannot carry this.
9. **Promote to memory on resolve.** Figma separates transient comments from durable Dev Mode annotations on the node, and Lovable, Subframe and Stitch all keep an always-read intent document. When the human resolves a thread whose outcome is a rule ("primary buttons are never full width on desktop"), offer to turn it into a design memory note with a `{{layer:...}}` reference. Feedback then becomes convention.

### Skip, for now

- In-tool chat, prompt queues, interrupt buttons. The harness owns those.
- Drawn annotations as the target. Pixels do not anchor. A screenshot attachment on a layer-anchored annotation covers the "look at this" case.
- Auto-resolve on send (Bolt). It erases the information the human needs.
- Variation trays and generated controls. Agents can write variants as boards.
- Comments that are only notes between people, without an agent flag. Useful later, not needed to prove the loop.

### Changes to the proposed shape

- **One file per thread, not one file per design.** Store threads as `.trickroom/designs/<designId>/annotations/<threadId>.json`. This mirrors `boards/<boardId>.json`, for the same reasons. The human adds and resolves threads while the agent replies on others, and one shared file would make those writes conflict or force a merge step. Two branches that each add feedback touch no shared file. A git diff shows one thread per file. Component-editor threads go next to the component in the system folder.
- **Agent replies are thread entries that point at change records.** They are not change records on their own. Some replies change nothing (questions, dismissals), and some writes address several annotations.
- **Surfacing needs a cursor and a size bound.** Covered in 6.
- **Naming.** `feedback_submit` already means "an agent reports a problem with Trickroom". Call this feature annotations (`annotation_list`, `annotation_reply`, `addresses` on `design_apply`) so neither agents nor docs confuse the two.
- **Migrations.** Annotation files are a new persisted userland shape. Give them a `version` field and a migration path from day one, as the design files and memory notes have.

### A later steering feature

The research suggests steering is a small extension of annotations, not a separate surface:

- **Board- and design-level annotations** with an `intent` (`change`, `question`, `approve`, plus a `priority` order the human can drag, after the reorderable queues in Make, v0 and Bolt). The agent sees them through the same delivery path.
- **Board holds that the server enforces.** A human marks a board "hold", and `design_apply` refuses writes to it with a clear status until the hold is lifted. No chat product can offer this, because none of them sits in the agent's write path as a separate service. We do, and it turns "stop touching the header" from a hope into a guarantee.
- **Agent presence.** Show which boards an agent is working on, inferred from recent writes and reads in the session. An explicit "working on these layers" call would also work, after Paper's reported `start_working_on_nodes` (UNVERIFIED) and the Figma agent's loading indicators. This answers the designer's question "has it seen my note yet" alongside the `acknowledged` state.
- **Approve before write.** For large plans, the agent posts a plan as a reply in `needs_input`, and the human approves in the editor. This copies Linear's elicitation and Figma Make's plan mode without a chat.

## Open questions

1. **Commit annotations or not?** Drawbridge commits its task files, while Agentation and Vibe keep everything in `~/`. Committing fits our principles and makes feedback reviewable, but resolved threads pile up in history. Options: commit everything; commit open threads and archive resolved ones; or a project setting. Decide before the file layout is fixed.
2. **Who may resolve?** Proposal above: human only, agent proposes. Some users will want agents to close trivial threads. Should that be a project setting?
3. **Does sending require the editor?** If a human writes an annotation through the REST API or by editing the JSON, is it "sent"? Probably yes, which means the draft state must never touch disk.
4. **Multiple agents.** Two agent sessions on one design both see a new annotation. Does `acknowledged` act as a claim, so the second agent skips it? Agentation does not say. We need a rule before parallel agents are common.
5. **Revert depth.** Keeping before-state per change record grows the files. Keep it for open and addressed threads only, and drop it on resolve?
6. **Annotations as prompt input.** Annotations are instructions read by agents with write access. In a shared repo, a thread from a teammate's branch is someone else's prompt. Do we mark authors and tell the agent to treat other authors' threads with care, as the Channels docs warn for unauthenticated senders?
7. **Canvas selection first?** The Layers rail is the only way to select today. Click-to-select on the canvas may need to ship before annotations, or annotating will feel like filling in a form.
8. **Component-editor anchors.** A component node exists per variant combination in the editor view. Does an annotation anchor to the node in general, or to the node at specific variant values?
